Real-browser validation of Web Kiosk **1.0.30** (the version synced to
[music-assistant/server#6948](https://github.com/music-assistant/server/pull/6948))
on 2026-10-15.

## Environment

| Item | Value |
|------|-------|
| Music Assistant | `music-assistant/server` `dev` at `a12a4b9`, run from source in an isolated data directory |
| Provider | Web Kiosk 1.0.30, linked into `music_assistant/providers/web_kiosk` |
| Browser | Chromium 154 (Playwright), one HTML5 kiosk and one Sendspin kiosk |
| Media | Local files provider, one album with four 25-second tracks |
| Audio tooling | FFmpeg 7.0.2 |

Commands were sent through the Music Assistant JSON-RPC API. Queue and player
state were sampled every 1–1.5 s; browser state was read from the kiosk page.

## Results

| # | Scenario | Observed | Result |
|---|----------|----------|--------|
| T1 | Album playback on an HTML5 kiosk (`ENQUEUE`) | Each track handed over in advance; on track end the kiosk started the next one and the MA queue index followed 0 → 1 → 2 → 3; after the last track queue and player went `idle` and MA marked the queue ended | Pass |
| T2 | Pause, repeated pause, resume, seek, volume | Position held at 4.8 s through two pauses; resume and seek continued correctly; volume 35 reached the page slider | Pass |
| T3 | Announcement in the middle of a track | Announcement played; the track resumed at its position (11.7 s → 12.9 s) without skipping. Total announcement time 6.8 s for a 4 s clip (MA minimum wait) | Pass after fix (see below) |
| T4 | Page reload during playback | Playback continued from the same position (12.9 s → 15.1 s); title and volume restored | Pass |
| T5 | `next`, `previous`, `play_index`, end of queue, play after end, `stop` | All transitions followed the queue; play after the queue ended restarted the album | Pass |
| T6 | Disable and enable a kiosk with its browser connected | Disabled kiosk left the registry and rejected playback; enabling registered the connected browser again without a reload and it played | Pass |
| T7 | Sendspin kiosk, first ungrouped playback | Playback selected the linked Sendspin output; MA streamed the queue over Sendspin and advanced tracks | Pass |
| T8 | Browser stream failure | A real `MediaError` produced a `playback_error` report with the playback generation; the server logged it and the kiosk went `idle` | Pass |

## Issue found and fixed during the run

**Announcements waited for the MA safety timeout (T3).** The announcement
controller holds the player's playback lock until the player reports `idle`,
while the track-end and stream-failure handlers acquired the same lock first.
Every announcement therefore ended only after `duration + 10 s` (14.8 s for a
4 s clip). Since queue progression moved to `ENQUEUE`, these handlers issue no
Music Assistant command, so they no longer take the lock. Fixed in 1.0.30 with
a regression test; re-run: 6.8 s.

## Open items (not regressions of this version)

1. After a Sendspin-to-HTML5 fallback the device does not return to Sendspin
   until Music Assistant restarts: the fallback unregisters the Sendspin
   protocol player and a reconnecting browser does not register it again.
   This needs a core way to move playback between a player's outputs.
2. In a contrived sequence (Sendspin disconnect, fallback, page reload,
   second fallback) the second fallback resumed past the end of the track and
   the browser reported a stream error.
3. The bundled `sendspin-js` 5.0.0 is accepted by `aiosendspin` 10.1 through
   its compatibility layer, which logs "non-compliant client" warnings.
4. Cosmetic: the "Playback failed" status is cleared by the following stop
   message, and `/favicon.ico` returns 404.
