# Общий Sendspin JS для Web Kiosk и фронтенда MA

Исследовано 2026-10-13. Это анализ исходников и установленного пакета, без изменения провайдера или работающего MA.

## Вывод

**Да, общую поставку использовать можно, но текущий фронтенд не предоставляет пригодный публичный SDK asset. Просто заменить `import('./sendspin-js/index.js')` ссылкой на существующий `/assets/index-*.js` нельзя считать рабочим решением.** Нужен небольшой контракт в `music-assistant/frontend`: отдельная ESM точка входа с публичными экспортами SDK и метаданными версии. После выпуска соответствующего frontend wheel провайдер сможет обслуживать эти ресурсы из установленного пакета и удалить собственные Sendspin/Noble файлы. Это архитектурная рекомендация; такая сборка ещё не реализована и не проверена в браузере.

## Что реально находится в wheel

Проверен `.venv/ci-upstream/lib/python3.14/site-packages/music_assistant_frontend` версии 2.17.339. Здесь есть HTML и готовые hashed assets, но нет дерева `node_modules/@sendspin` или отдельного Sendspin ESM entry. SDK, crypto и Noise identity код находятся в `assets/index-5eQzvEL3.js` (356444 байта; SHA256 `6d9f5eae7270a1e0fffe57786eb6811d033dc088f57944eee24dbb2a158f35c2`). Этот модуль при загрузке выполняет инициализацию Vue и `mount('#app')`; экспортирует внутренние сокращённые имена приложения, а не контракт `SendspinPlayer` / `loadSendspinClientIdentity`. Имеются отдельные `libopus-decoder-CL3HGyIN.js` и `oggOpusDecoder-D_t9a72E.js`. Это прямое наблюдение установленного wheel, а не предположение по package.json. [Официальная версия поставки](https://github.com/music-assistant/frontend/releases/tag/2.17.339).

Vite собирает приложение в `music_assistant_frontend`, использует `base: './'` и группы разделения чанков. Для SDK не задана отдельная точка входа, library build или стабильный экспорт. Простое выделение vendor chunk тоже недостаточно: нужны явно сохраняемые публичные экспорты и отсутствие запуска приложения. [Vite config](https://github.com/music-assistant/frontend/blob/f6d0a7055f647ed28b8e1679822adfdcb5f2f93c/vite.config.ts).

## Пути, origin и авторизация

Core получает каталог wheel через `music_assistant_frontend.where()` и обслуживает `/assets` из него. Это готовый транспорт для будущего общего SDK, но сегодня там только внутренние build assets. Статические ответы не добавляют общий CORS header; отдельные CORS обработчики для API не делают `/assets` доступным для cross-origin ESM. Kiosk по умолчанию обслуживается своим aiohttp сервером на 8098, поэтому импорт из core с другим портом потребует отдельного решения для origin. Также нужно учитывать HTTPS, HA ingress prefix и относительные импорты decoder chunks. [Core frontend routes](https://github.com/music-assistant/server/blob/50ae4dc2f6e82f562d752125fc999bd37221de0b/music_assistant/controllers/webserver/controller.py), [static helper](https://github.com/music-assistant/server/blob/50ae4dc2f6e82f562d752125fc999bd37221de0b/music_assistant/helpers/webserver.py), [Kiosk HTTP server](https://github.com/trudenboy/ma-provider-web-kiosk/blob/89ac255368a13f17d4ebf2ce9eb8d93f2a1976e1/provider/http_server.py).

Наиболее компактный вариант: Kiosk обслуживает разрешённый каталог общих SDK ресурсов **на своём origin**, читая его из установленного wheel. Он не копирует исходники в provider tree; сохраняются относительные импорты и прежний origin browser storage. Браузерные кеши разных origin при этом не становятся одним кешем: исчезает дублирование поставки и сопровождения библиотек, а не обязательно повторная загрузка каждым браузером. Альтернатива — перенести страницу Kiosk на core origin, но это шире задачи.

Сам SDK не привязан к фронтенду MA. Он предоставляет `SendspinPlayer`, identity helper, `baseUrl` и возможность передать собственный WebSocket. Совместная поставка кода не переиспользует уже созданный player/session из другой вкладки MA: в документе Kiosk создаётся собственный экземпляр. Код подключения MA поверх SDK — другой слой: token authentication, ingress и WebRTC. Core `/sendspin` ожидает первым сообщением MA auth; Kiosk сейчас подключается непосредственно к Sendspin на 8927. Поэтому переиспользование SDK не требует менять транспорт, а простая смена `baseUrl` на core без auth adapter сломает подключение. [SDK public API](https://github.com/Sendspin/sendspin-js/blob/7d103075138dda5c8909045647bb42b33c2d44fc/src/index.ts), [SDK socket support](https://github.com/Sendspin/sendspin-js/blob/7d103075138dda5c8909045647bb42b33c2d44fc/README.md), [MA connection adapter](https://github.com/music-assistant/frontend/blob/f6d0a7055f647ed28b8e1679822adfdcb5f2f93c/src/plugins/sendspin-connection.ts), [core auth proxy](https://github.com/music-assistant/server/blob/50ae4dc2f6e82f562d752125fc999bd37221de0b/music_assistant/controllers/webserver/sendspin_proxy.py).

Identity хранится в localStorage origin страницы. Внешний URL модуля не переносит storage на origin модуля. При сохранении страницы на 8098 прежний cryptographic client id можно сохранить; перенос страницы на core origin потребует отдельно решить миграцию identity, иначе Kiosk получит новый id или начнёт пользоваться identity штатного Web Player этого origin. Этот id связывает browser client с server bridge. MA также использует `productName: 'Web Player'` и регистрацию pairing через собственный API; Kiosk должен сохранить `productName: 'Web Kiosk'` и свою bridge регистрацию. [SDK identity storage](https://github.com/Sendspin/sendspin-js/blob/7d103075138dda5c8909045647bb42b33c2d44fc/src/client-identity.ts), [MA player integration](https://github.com/music-assistant/frontend/blob/f6d0a7055f647ed28b8e1679822adfdcb5f2f93c/src/components/SendspinPlayer.vue), [Kiosk bridge](https://github.com/trudenboy/ma-provider-web-kiosk/blob/89ac255368a13f17d4ebf2ce9eb8d93f2a1976e1/provider/sendspin_bridge.py).

Версия API совпадает, однако Kiosk использует частные callback поля `core['_'+name]`, чтобы перехватить stream events, и ограничивает codecs до FLAC/PCM без WebCodecs, поскольку opus-encdec не vendored. Общее SDK должно сохранять используемые экспорты и совместимость callback поведения; codec расширение можно рассматривать отдельно, после проверки полного decoder graph. [Kiosk integration](https://github.com/trudenboy/ma-provider-web-kiosk/blob/89ac255368a13f17d4ebf2ce9eb8d93f2a1976e1/provider/static/web/web.js), [SDK decoder](https://github.com/Sendspin/sendspin-js/blob/7d103075138dda5c8909045647bb42b33c2d44fc/src/audio/decoder.ts).

## Варианты и рекомендуемый порядок

| Вариант | Результат |
| --- | --- |
| Найти hashed app chunk и импортировать его | Нет устойчивого API; запускается приложение, имена и зависимости меняются при сборке. Не рекомендуется. |
| Генерировать SDK bundle из npm в provider CI | Убирает ручное сопровождение десятков файлов, но библиотека всё ещё дублируется в поставке. Возможный временный вариант. |
| Выпускать SDK asset в frontend wheel | Рекомендуется: общий version pin, одна поставка и штатное обновление через dependency MA. |
| Встроить Kiosk как экран штатного frontend | Максимальное переиспользование player/auth/decoder, но значительно более крупная переработка. |

Минимальный upstream seam: frontend multi-entry build с отдельным публичным ESM wrapper (`SendspinPlayer`, `loadSendspinClientIdentity`), версией API/SDK и описанным расположением ресурсов в wheel. Общий dependency graph должен использовать одну SDK/Noble копию для wrapper и приложения, а не независимо собирать два self-contained bundle. Entry не должен импортировать Vue app, store или MA auth. Decoder assets и лицензии также должны попасть в wheel; относительные URL должны работать при обслуживании с prefix. Python API пакета может предоставлять SDK resource directory/manifest, чтобы провайдер не искал hashed filenames.

Дальше: выпуск frontend wheel → обновление frontend pin в server → миграция Kiosk через provider release/sync с удалением vendor tree. На поддерживаемых версиях без этого контракта нужен явно определённый минимум MA либо временный fallback; автоматически извлекать код из app bundle не следует. Browser checks для миграции: импорт без запуска Vue, сохранение identity, bridge takeover и pairing, native Opus/FLAC/PCM, возможный fallback Opus, HTTP/HTTPS/ingress, reconnect и синхронное воспроизведение. Сейчас исследование подтверждает возможность архитектуры, но не её runtime работоспособность.
